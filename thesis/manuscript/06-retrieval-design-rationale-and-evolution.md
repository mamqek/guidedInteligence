# Retrieval Design Rationale and Evolution

The retrieval architecture described in Chapter 5 emerged from a sequence of formative experiments rather than from a fixed initial design. These experiments repeatedly exposed a difference between finding source that appeared relevant and constructing a bounded, auditable set of evidence that covered the requested mechanism. The resulting changes concerned what the request asked retrieval to establish, how structural information could be used reliably, how source could be represented within limited model context, and which decisions could be delegated to an LLM without making evidence survival unpredictable.

This chapter presents that development by problem rather than chronology. It includes only experiments that explain a retained architectural decision, justify a rejected alternative, or establish a remaining limitation. Chapter 4 defines the experimental procedure and final comparison design, while Chapter 5 describes the resulting implementation. The purpose here is to explain why that implementation took its present form.

## Stabilizing Retrieval Requirements and Query Signals

Early native retrieval translated a repository request into search in two main ways. Request analysis assigned broad evidence roles—such as implementation, test, configuration, and documentation—to indicate which kinds of source should be retrieved. BM25-first search then ranked source ranges through literal overlap with identifiers and other terms produced during that analysis. Both mechanisms were useful but imprecise. Covering the expected roles did not ensure that the retrieved source explained the complete behaviour, while literal matching could prioritize unrelated source containing similar terminology. The latter problem became less predictable when request analysis presented inferred conceptual phrases as if they were exact identifiers. The design addressed these failures through evidence obligations, deterministic anchor validation, and hybrid semantic and lexical retrieval.

The first problem concerned evidence roles. These roles described the general type of an artifact rather than the particular claim it established. A request about why a change propagates could therefore retrieve an implementation that updates state and a test that observes the final result, yet still miss the caller that initiates the update or the code that carries its effect forward. The expected roles would appear covered even though the behavioural chain remained incomplete. The revised design introduced central intent classification and derived evidence obligations from the response stages associated with the selected intent. Each obligation identifies a claim or transition for which repository support is required. Roles remain useful for describing source categories, but they no longer determine whether the requested mechanism is complete. In ten post-change Vue analyses, requests that had previously collapsed into one broad implementation requirement instead produced six to eight stage-linked obligations. Only two runs reached `strong/true`, showing that more precise requirements exposed later retrieval failures rather than solving them automatically.

The second problem concerned which request terms received exact-match authority. Request analysis could interpret a conceptual phrase as a source identifier, divide a complete command into fragments, or omit an explicitly stated error. Identical requests could therefore produce different exact anchors, even though exact retrieval should depend on information literally supplied by the user. Prompt instructions alone did not stabilize this behaviour. The retained design deterministically checks proposed paths, symbols, commands, versions, and error messages against the request before accepting them as exact anchors. Model-generated concepts remain available as ordinary search terms, but they cannot constrain retrieval as if the user had named them directly. Before this correction, two TypeScript analyses placed an important implementation file at substantially different admission positions because their anchor inventories differed. Two focused repeats after the correction produced the same paths, symbol, command, version, and error anchors. In the subsequent full-pipeline pair, the principal Builder, BuilderState, and WatchMode files were admitted consistently, although conceptual query wording and later evidence decisions continued to vary.

The third problem concerned how literal and semantic signals influenced retrieval. BM25-first search strongly rewarded repeated words and identifiers, which was useful when the request contained an exact repository name but misleading when common terminology appeared across unrelated files. A file could therefore rank highly because it shared vocabulary with the request rather than because it implemented the required behaviour. Qdrant replaced BM25 as the active retrieval backend and received two distinct query formulations for each obligation. The semantic formulation expresses the required behaviour, while the lexical formulation preserves confirmed identifiers and other literal terms. Dense and sparse retrieval results remain separately observable before reciprocal-rank fusion combines them. This structure allows conceptual similarity and exact terminology to contribute without treating either as proof of relevance. BM25 remains available for supporting index operations, but it no longer controls the active repository-retrieval path. Because this transition was not isolated in the frozen evaluation, it defines the retained search design without establishing that hybrid retrieval alone caused an improvement in final quality.

Together, these decisions separated responsibilities that the earlier retrieval design had mixed together. Intents and obligations define what repository evidence must be established. Deterministic anchor validation decides which request terms may act as exact constraints. Hybrid retrieval then combines behavioural meaning with confirmed literal terminology. The resulting boundary is more stable and auditable, while semantic interpretation remains available where deterministic rules cannot define the requested mechanism.

## From Broad Graph Expansion to Source-Grounded Structural Navigation

Structural retrieval initially presented two different problems. The original CGC backend was operationally unsuitable for the evaluated repositories: a historical TypeScript run exhausted a 600-second structural-indexing limit before useful retrieval, and its structural output relied partly on broad heuristic matching. Replacing it with the project-local CodeGraph made exact owner and relationship queries practical; on the same historical case, CodeGraph indexing completed in seconds rather than becoming the blocking stage. This replacement established a usable structural substrate, but it did not show that giving graph structure greater influence would improve the final evidence.

Several subsequent experiments gave graph connectivity too much authority. Semantic seeds were expanded into large connected neighborhoods, structural degree and accumulated edge scores influenced ranking, and long paths were treated as possible mechanism evidence. The resulting graphs were often internally connected but semantically wrong. In one TypeScript trace, the highest-scoring ten-node path remained mostly inside test setup and status-reporting code. It accumulated structural reward without reaching the production factory, state-update, propagation, or diagnostic responsibilities needed by the issue. Other experiments that serialized readable relationship descriptions or selected CodeGraph snippets directly amplified generic member collisions and produced unstable Oracle overlap. Connectivity showed that code elements were related, but not that the relationship answered the request.

The retained redesign reversed this dependency. Repository searches first produce source observations; those observations must be disclosed and semantically qualified before they ordinarily become roots for structural exploration. CodeGraph can then establish canonical owner identity, resolve an exact target, or verify a bounded relationship from already grounded source. Graph metadata remains provenance and navigation support rather than independent factual evidence, and a newly reached target must be inspected and qualified on its own. This qualification-first boundary reduced the ability of weak semantic matches to generate large graph neighborhoods and moved model effort from one enormous final graph-selection request into bounded decisions over visible source.

CodeGraph is also not treated as a complete account of every supported language. Some JavaScript and Python callables are created through assignments that do not receive a suitable graph owner. Language-routed AST analysis was therefore retained as a narrow source-derived complement for owner boundaries and visible calls. These records do not become invented graph nodes; they fill a concrete representation gap while preserving exact source as the authority.

The resulting role for structural retrieval is intentionally narrower than the earlier graph-first designs. It is retained because it can identify owners and make exact, inspectable navigation possible, not because high connectivity is assumed to imply relevance. Whether these capabilities improve localization, evidence survival, or mechanism completeness is an empirical question addressed by the CodeGraph ablation in Chapter 7.

## Representing Retrieved Source Within Bounded Context

Even correctly retrieved source cannot be passed to every LLM stage without selection. The same range may be returned for several obligations and through both dense and sparse retrieval, while a short matching range may resolve to an owner containing hundreds of lines. Treating every occurrence separately wastes context; replacing every occurrence with the complete owner can exceed the available input before other files are considered. The design therefore had to preserve identity and useful context without assuming that either the original chunk or the complete enclosing owner was always the correct unit.

The initial pipeline handled candidates repeatedly within separate obligation and file groups. Representatives were selected early, alternative ranges were held behind them, and selected owners were canonicalized and clipped again after comparison. This made it difficult to determine whether a source had been absent, hidden behind another range from the same file, selected and later removed, or duplicated under several identities. It also allowed a few files containing many owners to consume most of the comparison request.

The canonical-snippet redesign resolved all retrieved ranges before admission and merged repeated occurrences into one source identity with their combined query, channel, anchor, and obligation provenance. Admission could then compare globally ranked snippets while using file grouping only to serialize them efficiently. Same-input counterfactuals showed the practical effect: inputs that the earlier whole-file policy represented as 92 snippets from seven files and 91 snippets from four files became 64 snippets from 21 files and 71 snippets from 22 files, respectively, at a smaller request size. The two live comparisons reduced combined owner-comparison tokens by 19.3% and retained the three focal implementation files, although the final results remained partial. The experiment justified the admission boundary without claiming that it solved downstream sufficiency.

More aggressive representations were less successful. Evidence regions grouped nearby or related owners into larger units, reducing one candidate population by 14%, but the request still filled its character limit, comparison cost did not fall, and an unchanged repeat violated the existing selection contract. A preferred-size prefix substantially reduced comparison input and tokens, but its first form exposed a separate conflict: the model selected several distinct and relevant owners from the same central files, while the old runtime allowed at most two. The useful lesson was not that smaller input should replace semantic selection. It was that input admission and the selection contract had to be redesigned together; compression that merely moved the failure to a later validator was not a valid improvement.

Source disclosure created a second boundary. Structural resolution can identify the correct owner while the bounded source view shows only its signature or an early fragment, causing qualification to judge an incomplete presentation. Complete-owner reservation and LLM-guided inspection were tested as possible repairs. Their mechanics worked in focused fixtures and saved-source replays, but naturally retrieved small owners were usually already complete, whereas genuinely large owners often fell outside the proposed inspection rule. Forced reservation also produced unstable live outcomes and sometimes spent capacity on irrelevant test owners. Those variants were removed rather than retained on mechanical correctness alone.

The final compromise uses bounded owner-aligned disclosure and preserves a limited opportunity to continue an identified owner later. It does not pretend that context loss has been eliminated. Instead, the trace records whether the source shown for an owner was complete and where a character boundary omitted material. This makes incomplete presentation distinguishable from retrieval absence while avoiding unconditional full-owner expansion.

## Preventing Useful Evidence from Disappearing

Formative traces showed that evidence loss continued after retrieval and qualification. A relevant observation could belong to an inactive evidence island, a cross-file trace could lose its exact source representation, or the final evidence limit could fill before an accepted structural participant was appended. These were not equivalent to failing to retrieve the relevant file. They were representation and capacity failures at later stages.

The mixed-island file-trace experiment followed one such chain in the TypeScript case. The controller reached the relevant WatchMode source and recorded repeated calls into the Helpers file, but successive runs exposed different losses: the trace was associated with an already covered obligation, its localized destination was rejected, and an accepted trace later arrived after the evidence cap was full. The retained repair preserved the exact trace source, evaluated trace eligibility after deterministic representation, and reserved capacity only when the existing trace-selection stage accepted the structural participant. Two final runs retained Builder, BuilderState, WatchMode, and Helpers without increasing the action, round, graph-call, or final-evidence limits. Both remained `partial/false`, correctly reflecting that a file-level trace identifies a likely participant but does not prove its internal behaviour.

Evidence islands exposed a related selection problem. Comparing only a small set of complete islands could omit individually useful qualified observations, while adding whole islands could make the final request unbounded. Baseline-seeded island packets therefore began with every candidate already required by the ordinary selection policy and used only residual capacity for coherent companions. Across the measured Pandas, TypeScript, and Vue runs, every mandatory seed survived. The representation was retained because it could add context without silently replacing the established baseline candidates.

Dormant evidence required a different mechanism. Owner comparison sometimes left several already retrieved owners in a file that produced no qualified observation. Discarding them made the earlier character and selection limits irreversible; reprocessing every dormant file would recreate the original context problem. The retained recovery action spends one bounded opportunity on one eligible file and sends any disclosed owners through normal qualification. It recovered `Series::_binop` in the motivating Pandas run, but related experiments also established its limits. Broad ranking rules selected generic files, delayed scheduling changed the candidate population before recovery, and two-file batching helped only when the correct pair already occupied the first positions. These variants were rejected, while the single bounded recovery path and its explicit lifecycle records were retained.

Together, these experiments changed the meaning of omission. Deferred, dormant, inactive, rejected, and budget-excluded material remains distinguishable in the trace, and selected recovery mechanisms can revisit only narrowly defined subsets. Recovery is not a hidden fallback and does not grant preserved material evidential status. It offers another inspected and qualified opportunity while keeping the original resource limits visible.

## Keeping Exploration Application-Controlled

The qualification-first controller separated semantic judgments across qualification, coverage assessment, and action selection. An alternative experiment tested whether one persistent LLM planner could combine those decisions, maintain the retrieval state, and choose typed actions for each round. Application logic still validated and executed its requests, so the experiment changed decision ownership without granting unrestricted repository access.

The planner was mechanically viable and used fewer decision tokens. Two complete runs each executed three planner decisions and six validated native actions, with planner usage roughly one third below the qualification-and-coverage usage of the native reference run. The quality result nevertheless regressed from the reference's `strong/true` assessment to `partial/false` in both planner runs. More importantly, the exact same `Series::_binop` observation survived retrieval, grouping, structural resolution, and initial admission in both runs but was treated differently by planner qualification. It disappeared before the final candidate pool in one run and survived in the other.

The experiment was rejected because lower cost did not compensate for unstable destruction of central evidence. The retained allocation gives LLMs bounded semantic tasks, while application logic owns candidate identities, lifecycle transitions, action construction, scheduling, execution limits, and stopping enforcement. This does not remove model variability, but it exposes the boundary at which a semantic decision changes the evidence and prevents a single opaque planner state from controlling the complete process.

## What the Final Pipeline Still Does Not Solve

The retained decisions improved the observability and survival of repository evidence, but they did not remove the principal distinction that emerged during development: correct localization is not the same as a complete mechanism account. A pipeline may retrieve the implementation owner yet miss the caller that activates it, the state transition it triggers, or the downstream effect that explains the reported behaviour. A verified graph edge may reveal a likely handoff while the destination source remains unqualified. Conversely, a file can score well against an Oracle even when the selected ranges do not establish the causal relationship for which that file matters.

The experiments also leave genuine trade-offs. Canonical admission improves competition among retrieved source but still operates under a context boundary. Bounded recovery can expose an omitted owner but cannot guarantee that it wins qualification or final selection. Source-grounded structural navigation suppresses graph noise but may miss dynamic registration and relationships unavailable to static analysis. Separating semantic decisions makes losses traceable without making those decisions deterministic.

These limitations define the questions carried into the final evaluation. The CodeGraph comparison must distinguish file localization from owner grounding and connected-mechanism evidence. The adaptive-controller comparison must determine whether later exploration recovers useful material rather than merely increasing candidates and cost. Their combined ablation must show whether either capability depends on the other, while the Codex comparison examines a substantially different allocation of navigation and stopping responsibility. Chapter 7 therefore evaluates not only which files appear in the final ranking, but also where relevant evidence first disappears, whether required mechanism transitions survive, how stable the results are across repetitions, and what resources each configuration consumes.
