# Retrieval Design Rationale and Evolution

The retrieval architecture described in Chapter 5 emerges from a sequence of formative experiments rather than from a fixed initial design. These experiments repeatedly expose a difference between finding source that appears relevant and constructing a bounded, auditable set of evidence that covers the requested mechanism. The resulting changes concern what the request asks retrieval to establish, how structural information can be used reliably, how source can be represented within limited model context, and which decisions can be delegated to an LLM without making evidence survival unpredictable.

This chapter presents that development by problem rather than chronology. It includes only experiments that explain a retained architectural decision, justify a rejected alternative, or establish a remaining limitation. Chapter 4 defines the experimental procedure and final comparison design, while Chapter 5 describes the resulting implementation. The purpose here is to explain why that implementation took its present form.

## Stabilizing Retrieval Requirements and Query Signals

Early native retrieval translates a repository request into search in two main ways. Request analysis assigns broad evidence roles—such as implementation, test, configuration, and documentation—to indicate which kinds of source should be retrieved. BM25-first search then ranks source ranges through literal overlap with identifiers and other terms produced during that analysis. Both mechanisms prove useful but imprecise. Covering the expected roles does not ensure that the retrieved source explains the complete behaviour, while literal matching can prioritize unrelated source containing similar terminology. The latter problem becomes less predictable when request analysis presents inferred conceptual phrases as if they are exact identifiers. The design addresses these failures through evidence obligations, deterministic anchor validation, and hybrid semantic and lexical retrieval.

The first problem concerns evidence roles. These roles describe the general type of an artifact rather than the particular claim it establishes. A request about why a change propagates can therefore retrieve an implementation that updates state and a test that observes the final result, yet still miss the caller that initiates the update or the code that carries its effect forward. The expected roles appear covered even though the behavioural chain remains incomplete. The revised design introduces central intent classification and derives evidence obligations from the response stages associated with the selected intent. Each obligation identifies a claim or transition for which repository support is required. Roles remain useful for describing source categories, but they no longer determine whether the requested mechanism is complete. In ten post-change Vue analyses, requests that the earlier design collapses into one broad implementation requirement instead produce six to eight stage-linked obligations. Only two runs reach `strong/true`, showing that more precise requirements expose later retrieval failures rather than solve them automatically.

The second problem concerns which request terms receive exact-match authority. Request analysis can interpret a conceptual phrase as a source identifier, divide a complete command into fragments, or omit an explicitly stated error. Identical requests can therefore produce different exact anchors, even though exact retrieval should depend on information literally supplied by the user. Prompt instructions alone do not stabilize this behaviour. The retained design deterministically checks proposed paths, symbols, commands, versions, and error messages against the request before accepting them as exact anchors. Model-generated concepts remain available as ordinary search terms, but they cannot constrain retrieval as if the user names them directly. Before this correction, two TypeScript analyses place an important implementation file at substantially different admission positions because their anchor inventories differ. Two focused repeats after the correction produce the same paths, symbol, command, version, and error anchors. In the subsequent full-pipeline pair, the principal Builder, BuilderState, and WatchMode files enter admission consistently, although conceptual query wording and later evidence decisions continue to vary.

The third problem concerns how literal and semantic signals influence retrieval. BM25-first search strongly rewards repeated words and identifiers, which is useful when the request contains an exact repository name but misleading when common terminology appears across unrelated files. A file can therefore rank highly because it shares vocabulary with the request rather than because it implements the required behaviour. Qdrant replaces BM25 as the active retrieval backend and receives two distinct query formulations for each obligation. The semantic formulation expresses the required behaviour, while the lexical formulation preserves confirmed identifiers and other literal terms. Dense and sparse retrieval results remain separately observable before reciprocal-rank fusion combines them. This structure allows conceptual similarity and exact terminology to contribute without treating either as proof of relevance. BM25 remains available for supporting index operations, but it no longer controls the active repository-retrieval path. The evaluation does not isolate this transition, so it defines the retained search design without establishing that hybrid retrieval alone causes an improvement in final quality.

Together, these decisions separate responsibilities that the earlier retrieval design mixes together. Intents and obligations define what repository evidence must be established. Deterministic anchor validation decides which request terms may act as exact constraints. Hybrid retrieval then combines behavioural meaning with confirmed literal terminology. The resulting boundary is more stable and auditable, while semantic interpretation remains available where deterministic rules cannot define the requested mechanism.

## From Broad Graph Expansion to Source-Grounded Structural Navigation

Structural retrieval initially presents two different problems. The original CGC backend is operationally unsuitable for the evaluated repositories: a historical TypeScript run exhausts a 600-second structural-indexing limit before useful retrieval, and its structural output relies partly on broad heuristic matching. Replacing it with the project-local CodeGraph makes exact owner and relationship queries practical; on the same historical testcase, CodeGraph indexing completes in seconds rather than becoming the blocking stage. This replacement establishes a usable structural substrate, but it does not show that giving graph structure greater influence improves the final evidence.

Several subsequent experiments give graph connectivity too much authority. They expand semantic seeds into large connected neighborhoods, allow structural degree and accumulated edge scores to influence ranking, and treat long paths as possible mechanism evidence. The resulting graphs are often internally connected but semantically wrong. In one TypeScript trace, the highest-scoring ten-node path remains mostly inside test setup and status-reporting code. It accumulates structural reward without reaching the production factory, state-update, propagation, or diagnostic responsibilities needed by the issue. Other experiments that serialize readable relationship descriptions or select CodeGraph snippets directly amplify generic member collisions and produce unstable Oracle overlap. Connectivity shows that code elements are related, but not that the relationship answers the request.

The retained redesign reverses this dependency. Repository searches first produce source observations; those observations must be disclosed and semantically qualified before they ordinarily become roots for structural exploration. CodeGraph can then establish canonical owner identity, resolve an exact target, or verify a bounded relationship from already grounded source. Graph metadata remains provenance and navigation support rather than independent factual evidence, and a newly reached target must be inspected and qualified on its own. This qualification-first boundary reduces the ability of weak semantic matches to generate large graph neighborhoods and moves model effort from one enormous final graph-selection request into bounded decisions over visible source.

CodeGraph is not treated as a complete or infallible account of every supported language. Some JavaScript and Python callables are created through assignments that do not receive a suitable graph owner. A separate failure appears in Vue 10519: CodeGraph's JavaScript parser interprets Flow-annotated declarations as small `if` owners and truncates another callable, while generated bundles without the annotations produce complete owner boundaries. Because the pipeline trusts those boundaries, structural resolution replaces useful source ranges with incomplete fragments before semantic selection.

This failure motivates the source-validation boundary described in Chapter 5. Its purpose is to prevent unsupported graph boundaries from replacing intact retrieved source and to cover callable forms that CodeGraph does not represent suitably. Exact source therefore remains authoritative when structural identity cannot be established reliably.

The resulting role for structural retrieval is intentionally narrower than the earlier graph-first designs. It is retained because it can identify owners and make exact, inspectable navigation possible, not because high connectivity is assumed to imply relevance. Whether these capabilities improve localization, evidence survival, or mechanism completeness is an empirical question addressed by the CodeGraph ablation in Chapter 7.

## Representing Retrieved Source Within Bounded Context

Even correctly retrieved source cannot be passed to every LLM stage without selection. The same range may be returned for several obligations and through both dense and sparse retrieval, while a short matching range may resolve to an owner containing hundreds of lines. Treating every occurrence separately wastes context; replacing every occurrence with the complete owner can exceed the available input before other files are considered. The design therefore needs to preserve identity and useful context without assuming that either the original chunk or the complete enclosing owner is always the correct unit.

The initial pipeline handles candidates repeatedly within separate obligation and file groups. It selects representatives early, holds alternative ranges behind them, and canonicalizes and clips selected owners again after comparison. This makes it difficult to determine whether a source is absent, hidden behind another range from the same file, selected and later removed, or duplicated under several identities. It also allows a few files containing many owners to consume most of the comparison request.

The canonical-snippet redesign resolves all retrieved ranges before admission and merges repeated occurrences into one source identity with their combined query, channel, anchor, and obligation provenance. Admission can then compare globally ranked snippets while using file grouping only to serialize them efficiently. Same-input counterfactuals show the practical effect: inputs that the earlier whole-file policy represents as 92 snippets from seven files and 91 snippets from four files become 64 snippets from 21 files and 71 snippets from 22 files, respectively, at a smaller request size. The two live comparisons reduce combined owner-comparison tokens by 19.3% and retain the three focal implementation files, although the final results remain partial. The experiment justifies the admission boundary without claiming that it solves downstream sufficiency.

More aggressive representations prove less successful. Evidence regions group nearby or related owners into larger units, reducing one candidate population by 14%, but the request still fills its character limit, comparison cost does not fall, and an unchanged repeat violates the existing selection contract. A preferred-size prefix substantially reduces comparison input and tokens, but its first form exposes a separate conflict: the model selects several distinct and relevant owners from the same central files, while the old runtime allows at most two. The useful lesson is not that smaller input should replace semantic selection. Input admission and the selection contract must be redesigned together; compression that merely moves the failure to a later validator is not a valid improvement.

Source disclosure creates a second boundary. Structural resolution can identify the correct owner while the bounded source view shows only its signature or an early fragment, causing qualification to judge an incomplete presentation. Experiments test complete-owner reservation and LLM-guided inspection as possible repairs. Their mechanics work in focused fixtures and saved-source replays, but naturally retrieved small owners are usually already complete, whereas genuinely large owners often fall outside the proposed inspection rule. Forced reservation also produces unstable live outcomes and sometimes spends capacity on irrelevant test owners. We therefore remove those variants rather than retain them on mechanical correctness alone.

The final compromise uses bounded owner-aligned disclosure and preserves a limited opportunity to continue an identified owner later. It does not claim to eliminate context loss. Instead, the trace records whether the source shown for an owner is complete and where a character boundary omits material. This makes incomplete presentation distinguishable from retrieval absence while avoiding unconditional full-owner expansion.

## Preventing Useful Evidence from Disappearing

Formative traces show that evidence loss continues after retrieval and qualification. A relevant observation can belong to an inactive evidence island, a cross-file trace can lose its exact source representation, or the final evidence limit can fill before an accepted structural participant is appended. These outcomes are not equivalent to failing to retrieve the relevant file. They are representation and capacity failures at later stages.

The mixed-island file-trace experiment follows one such chain in the TypeScript testcase. The controller reaches the relevant WatchMode source and records repeated calls into the Helpers file, but successive runs expose different losses: the trace is associated with an already covered obligation, its localized destination is rejected, and an accepted trace later arrives after the evidence cap is full. The retained repair preserves the exact trace source, evaluates trace eligibility after deterministic representation, and reserves capacity only when the existing trace-selection stage accepts the structural participant. Two final runs retain Builder, BuilderState, WatchMode, and Helpers without increasing the action, round, graph-call, or final-evidence limits. Both remain `partial/false`, correctly reflecting that a file-level trace identifies a likely participant but does not prove its internal behaviour.

Evidence islands expose a related selection problem. Comparing only a small set of complete islands can omit individually useful qualified observations, while adding whole islands can make the final request unbounded. Baseline-seeded island packets therefore begin with every candidate already required by the ordinary selection policy and use only residual capacity for coherent companions. Across the measured Pandas, TypeScript, and Vue runs, every mandatory seed survives. We retain the representation because it can add context without silently replacing the established baseline candidates.

Dormant evidence requires a different mechanism. Owner comparison sometimes leaves several already retrieved owners in a file that produces no qualified observation. Discarding them makes the earlier character and selection limits irreversible; reprocessing every dormant file recreates the original context problem. The retained recovery action spends one bounded opportunity on one eligible file and sends any disclosed owners through normal qualification. It recovers `Series::_binop` in the motivating Pandas run, but related experiments also establish its limits. Broad ranking rules select generic files, delayed scheduling changes the candidate population before recovery, and two-file batching helps only when the correct pair already occupies the first positions. We reject these variants and retain the single bounded recovery path with its explicit lifecycle records.

Together, these experiments change the meaning of omission. Deferred, dormant, inactive, rejected, and budget-excluded material remains distinguishable in the trace, and selected recovery mechanisms can revisit only narrowly defined subsets. Recovery is not a hidden fallback and does not grant preserved material evidential status. It offers another inspected and qualified opportunity while keeping the original resource limits visible.

## Keeping Exploration Application-Controlled

The qualification-first controller separates semantic judgments across qualification, coverage assessment, and action selection. An alternative experiment tests whether one persistent LLM planner can combine those decisions, maintain the retrieval state, and choose typed actions for each round. Application logic still validates and executes its requests, so the experiment changes decision ownership without granting unrestricted repository access.

The planner is mechanically viable and uses fewer decision tokens. Two complete runs each execute three planner decisions and six validated native actions, with planner usage roughly one third below the qualification-and-coverage usage of the native reference run. The quality result nevertheless regresses from the reference's `strong/true` assessment to `partial/false` in both planner runs. More importantly, the same `Series::_binop` observation survives retrieval, grouping, structural resolution, and initial admission in both runs but receives different planner-qualification decisions. It disappears before the final candidate pool in one run and survives in the other.

We reject the experiment because lower cost does not compensate for unstable destruction of central evidence. The retained allocation gives LLMs bounded semantic tasks, while application logic owns candidate identities, lifecycle transitions, action construction, scheduling, execution limits, and stopping enforcement. This does not remove model variability, but it exposes the boundary at which a semantic decision changes the evidence and prevents a single opaque planner state from controlling the complete process.

## What the Final Pipeline Still Does Not Solve

The retained decisions improve the observability and survival of repository evidence, but they do not remove the principal distinction that emerges during development: correct localization is not the same as a complete mechanism account. A pipeline may retrieve the implementation owner yet miss the caller that activates it, the state transition it triggers, or the downstream effect that explains the reported behaviour. A verified graph edge may reveal a likely handoff while the destination source remains unqualified. Conversely, a file can score well against an Oracle even when the selected ranges do not establish the causal relationship for which that file matters.

The experiments also leave genuine trade-offs. Canonical admission improves competition among retrieved source but still operates under a context boundary. Bounded recovery can expose an omitted owner but cannot guarantee that it wins qualification or final selection. Source-grounded structural navigation suppresses graph noise but may miss dynamic registration and relationships unavailable to static analysis. Separating semantic decisions makes losses traceable without making those decisions deterministic.

These limitations define the questions carried into the final evaluation. The CodeGraph comparison must distinguish file localization from owner grounding and connected-mechanism evidence. The adaptive-controller comparison must determine whether later exploration recovers useful material rather than merely increasing candidates and cost. Their combined ablation must show whether either capability depends on the other, while the Codex comparison examines a substantially different allocation of navigation and stopping responsibility. Chapter 7 therefore evaluates not only which files appear in the final ranking, but also where relevant evidence first disappears, whether required mechanism transitions survive, how stable the results are across repetitions, and what resources each configuration consumes.
