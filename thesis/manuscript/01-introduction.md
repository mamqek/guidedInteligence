# Introduction

A developer investigating an unfamiliar repository rarely starts with a precise source location. Instead, the starting point is often a bug report or a question about an API. This describes observed behaviour, leaving the developer to find the code responsible for it. Lexical matching between a question and repository source offers a starting point. The harder task is deciding which source actually explains the behaviour and whether enough of it has been found to answer the question. Studies of developer information needs likewise distinguish locating code from understanding what it does and how its parts interact [@Ko2007InformationNeeds; @Sillito2008ProgrammingQuestions].

Language models can help navigate and explain repositories. However, research on retrieval-augmented question answering shows that providing relevant material does not guarantee that the generated claims follow from it [@Gao2023ALCE]. A coherent answer may still be irrelevant to the question or incorrectly explain the code. Checking such an answer requires identifying the code or other repository material that supports its claims. We refer to this supporting material as *repository evidence*. A file reference alone does not provide that detail. Relevant snippets can also disappear when a later stage must fit evidence into a limited context. These problems matter especially for assistance intended to help someone learn a codebase. Guided questions and follow-up explanations should rest on source that a reader can inspect, while acknowledging relationships that the available evidence does not establish. The thesis develops that form of assistance as a motivation; its empirical study concerns the retrieval of repository evidence rather than measured learning outcomes.

Research on code localisation [@Zhou2012BugLocator], repository question answering [@Peng2026SWEQA], structural navigation [@Petrenko2013DepIR], and agentic repository exploration [@Kang2024AutoFL] provides several ways to find relevant source. Search ranks relevant files, graph relationships can expose nearby code, and an agent can decide what to inspect next. The remaining difficulty for this thesis lies in what happens after source is first retrieved and before it is selected as evidence for an explanation. Useful source may be found early but shortened, deferred, or rejected as the result is assembled. A final file list alone does not show where that happened. Chapter 3 develops this gap against the relevant research.

## Research Problem and Questions

This thesis investigates how to construct repository evidence through a controlled process that records how source is found, assessed, and selected. These records make the process inspectable, following the provenance principle of documenting how a result is produced [@W3C2013PROV]. Its research artifact, Guided Intelligence, supports two ways of retrieving source code and other repository material. The native Workspace pipeline combines textual and semantic search with *structural resolution*, which associates retrieved snippets with the functions or other code constructs they belong to, followed by semantic assessment, bounded follow-up exploration, and final evidence selection. Application logic controls the order of retrieval stages, available actions, limits, and stopping rules; language models make narrower judgements within that process. Codex retrieval offers a second route in which an agent directs repository inspection. Both routes can supply evidence to the same downstream response and guided interaction.

The overarching objective is to construct and examine a controlled retrieval pipeline for questions about unfamiliar repositories. The study asks three related questions:

1. **RQ1:** How can retrieved source be turned into an evidence set whose support and selection history can be inspected?
2. **RQ2:** What effects do structural resolution using CodeGraph and bounded adaptive exploration have on file retrieval quality, exact required-evidence survival, stability, and cost?
3. **RQ3:** How does the complete Workspace pipeline compare with Codex retrieval in file retrieval quality, required-evidence completeness, stability, and cost?

Each question requires a different kind of answer. RQ1 concerns the design of the evidence process: how a retrieved source range receives an identity, how the system assesses what it supports, and how its later admission or rejection remains traceable. Chapters 5 and 6 answer it through the implemented pipeline and the experiments that shape its design. RQ2 concerns the contribution of two capabilities within Workspace. CodeGraph identifies structural owners and relationships in code; the adaptive controller can conduct further bounded exploration after initial evidence construction. The evaluation varies these capabilities independently and measures their effects on final files, exact required source, stability, and cost. RQ3 compares Full Workspace with Codex as complete retrieval systems. Their differences cannot be attributed to a single navigation decision because they also differ in how they search, stop, and choose final evidence.

## Research Approach and Contributions

The study combines the design and implementation of Guided Intelligence with a controlled evaluation of its repository retrieval. During development, focused tests and repeated pipeline runs reveal failures in selecting relevant source, resolving its structure, and retaining it through later stages. Changes are retained or rejected according to their observed effects, and Chapter 6 explains the decisions that lead to the evaluated design. The measured evaluation uses 35 *retrieval testcases* drawn from historical CodeRepoQA issues in the [TypeScript](https://github.com/microsoft/TypeScript), [pandas](https://github.com/pandas-dev/pandas), and [Vue](https://github.com/vuejs/vue) repositories. Each testcase pairs the original GitHub issue report with a repository snapshot from before the issue is resolved. Files identified from the later fix form the withheld *file-level evaluation oracle* [@Hu2025CodeRepoQA]. A separate *required-evidence reference* identifies the exact pre-resolution source needed to explain or verify each resolution.

We evaluate four Workspace configurations: Full Workspace with both CodeGraph and adaptive exploration, Workspace without CodeGraph, Workspace without adaptive exploration, and Workspace without either capability. *Adaptive exploration* refers to additional retrieval after initial evidence construction. A fifth condition evaluates Codex retrieval on the same cases. Each case and condition has four valid repetitions, producing 700 accepted runs. The measures assess file ranking and recovery, survival of the exact required source, repeated-run variation, time, and model-token use. Response generation is disabled so that the measured task is retrieval and final evidence selection. Workspace traces additionally identify the first recorded boundary at which missing required source disappears. Chapter 4 defines the corpus, comparison conditions, measures, and validity rules.

The thesis makes three connected contributions. First, it presents Guided Intelligence as a complete architecture for taking a repository question through evidence retrieval to a response and guided follow-up interaction. The native pipeline gives retrieved source a stable identity, preserves its discovery history in structured records, checks whether visible source supports a requested claim, and limits further exploration and final selection. Second, it documents formative experiments that explain why these boundaries and controls appear in the final design, including approaches that are rejected when they lose important source or introduce noise. Third, it evaluates the two native capabilities and compares the complete native route with Codex using the same file oracles, required-evidence reference, and repeated cases. The corpus-wide audit distinguishes finding a relevant file from retaining all defined source needed for the testcase.

Codex recovers more of the known implementation files, retains more required source, and produces more repeatable file sets. Full Workspace, however, more often ranks an implementation file first and uses substantially fewer model tokens. Adaptive exploration provides modest native retrieval gains at a considerable token cost. CodeGraph slightly improves recall and exact-source survival, but the additional structural information does not consistently improve the earliest file ranks. Even a complete required-source set establishes availability rather than proving that a model understands the relationships within it.

## Scope and Thesis Structure

The empirical subject of this thesis is repository retrieval and evidence construction. The study evaluates retrieval and evidence selection, not the correctness of generated explanations. The file oracle supports conclusions about locating known fixing files, while the required-evidence reference establishes whether defined pre-resolution snippets survive together. Neither measure proves that a response model correctly understands their causal relationship. The systems' own coverage and sufficiency labels are reported as outputs rather than treated as independent truth. Guided explanations and understanding checks are implemented, but their effect on learners is not measured. These boundaries guide the interpretation of the findings in Chapter 8.

Chapter 2 introduces the concepts needed to discuss repository evidence and retrieval. Chapter 3 places the work alongside research on code localisation, structural and agentic exploration, grounding, and learning support. Chapter 4 describes the research method. Chapter 5 presents the implemented architecture, and Chapter 6 explains the formative decisions behind it. Chapter 7 reports the measured results and selected case analyses. Chapter 8 interprets their implications and limitations, before Chapter 9 returns to the research questions and the thesis's overall contribution.
