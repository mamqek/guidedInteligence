# Background

Repository-level assistance requires more than matching a question to files that contain similar words. A behaviour may begin at one entry point, change program state elsewhere, and then pass into another component before its effect becomes observable. Different retrieval and structural-analysis techniques can help expose the code involved in this progression. Following how the behaviour moves through the repository can therefore help identify the source files relevant to the question. Determining how those files contribute to the behaviour is a program-comprehension task.

## Repository-Level Program Comprehension

Program comprehension concerns the construction of a mental model of software sufficiently accurate to answer a question or perform a change. Empirical studies show that developers ask questions at several levels: they locate code, determine what it does, trace how behaviour propagates, and investigate why a particular state or outcome occurs [@Ko2007InformationNeeds; @Sillito2008ProgrammingQuestions]. Questions at the latter levels often cross the boundary of one file or function. Explaining why an input produces an observed failure, for example, may require the caller that introduces the input, an intermediate transformation, and the component that exposes the incorrect result.

The evidence used to answer such questions can be represented at different granularities. A *file* is a repository-relative path and is the coarsest evidence unit used in this thesis's evaluation. A *source range* identifies contiguous lines within a file. The bounded source text taken from such a range and passed through the retrieval pipeline is referred to as a *snippet*. A *symbol* is a named program element, such as a function, method, class, or variable. A *structural owner* is the code construct to which a source range belongs. These units are related but not interchangeable. A correct file can be retrieved while the relevant function remains hidden, and a correct function can be shown without the caller or downstream effect needed to explain its role.

Repository evidence also differs by function. *Implementation evidence* contains production behaviour directly responsible for the question. *Supporting evidence* includes tests, declarations, configuration, and documentation that constrain, exercise, or describe that behaviour. A regression test can establish the expected result, but it does not necessarily reveal which implementation produces it. Conversely, implementation source may show a state update without making its externally visible consequence clear. Both forms can be useful, but they support different claims.

For this thesis, a *mechanism* is a connected account of how a relevant behaviour occurs. Its evidence may include an entry point, intermediate state changes, cross-file handoffs, and an observable effect. Not every question requires every element, and the required chain depends on the requested explanation. The important distinction is between relevance and coverage: source can be individually relevant while the evidence set remains insufficient to establish the requested mechanism.

## Retrieving and Structuring Repository Evidence

One way to locate relevant source is to compare the words and identifiers in a request with those used in repository files. Lexical retrieval performs this comparison through term-based representations and ranks source passages according to textual overlap. These representations are sparse because each passage contains only a small fraction of the repository vocabulary. Ranking models such as BM25 give greater influence to discriminative terms while normalising for document length and repeated occurrences [@Robertson2009BM25]. This makes identifiers, paths, commands, and error messages useful signals when the request contains them exactly. The same dependence on literal overlap can favour unrelated files that reuse common project vocabulary or miss behaviour described with different words.

Dense retrieval instead maps a query and candidate text into vector representations whose similarity reflects learned semantic relationships. It can retrieve conceptually related passages without requiring the same surface terms; dense passage retrieval demonstrates this principle by learning separate query and passage encoders and comparing their representations [@Karpukhin2020DPR]. Dense similarity is also imperfect. Semantically broad descriptions can match many plausible fragments, and exact identifiers may lose influence when they are absorbed into one vector representation.

Hybrid retrieval combines lexical and semantic rankings so that literal and conceptual evidence can contribute separately. Rank-fusion methods operate on result positions rather than assuming that scores from different retrieval systems are directly comparable. Reciprocal-rank fusion, for example, assigns each candidate a contribution based on its rank in each input list and sums those contributions; in their evaluation, Cormack et al. find that it outperforms the individual rankings it combines [@Cormack2009RRF]. Fusion can improve retrieval when the two rankings recover complementary relevant source, but it can also retain noise from either channel when their errors overlap. The resulting order remains a relevance estimate rather than evidence of correctness. It determines which source is inspected first, not whether that source establishes the requested claim.

Exact anchors impose a stricter boundary on how request terms may be used. Only information explicitly present in the request may be treated as a verified repository fact and used for exact lookup or strongly constrained search. Such an anchor has different authority from a term inferred by a model: an inferred phrase may be useful for query expansion, but treating it as a literal repository fact can direct retrieval to the wrong location. Separating exact anchors from generated search terms therefore preserves the difference between supplied information and interpretation.

Textual retrieval identifies promising source, but program structure can describe how that source belongs to the implementation. An abstract syntax tree represents the syntactic nesting of a program and can locate enclosing declarations or executable constructs. Calls, references, containment, inheritance, and dependencies can also be represented in a graph. Its nodes identify code constructs, and its edges represent known relationships between them. Program-graph research illustrates how syntactic and semantic edges expose relationships that sequential text alone does not represent directly [@Allamanis2018ProgramGraphs].

Structural representations can guide retrieval toward source that is likely to participate in the requested behaviour, but they cannot establish that participation by themselves. Static analysis does not always resolve dynamic dispatch, reflection, framework registration, generated code, or targets that depend on run-time data. It can also represent some language constructs unevenly; for example, a function assigned to a variable may be harder to identify consistently than a conventional declaration. A graph edge therefore records a relationship inferred by the analysis, not evidence that the relationship explains the request. The linked source still has to be inspected and assessed before it supports a claim.

## From Relevant Source to Evidence

Retrieval returns candidates; an evidence-construction process decides what those candidates can establish. The conceptual progression used in this thesis has five boundaries:

1. **Candidate retrieval** obtains source ranges using lexical, semantic, exact, or structural signals.
2. **Source and owner localisation** associates a range with the file, symbol, or enclosing implementation unit to which it belongs.
3. **Semantic qualification** assesses whether the visible source supports a required claim rather than merely sharing terminology with it.
4. **Relationship construction** connects qualified source across calls, state changes, dependencies, or other relevant handoffs.
5. **Final evidence selection** chooses the bounded set returned for downstream explanation or evaluation.

The boundaries matter because presence at one stage does not imply survival at the next. Relevant source can be retrieved but excluded by an input limit, mapped to an incomplete owner, rejected during qualification, disconnected from the rest of the mechanism, or displaced during final selection. A final list alone cannot distinguish these outcomes.

The pipeline also records the retrieval history of each candidate. This follows the general provenance principle of retaining information about the entities and activities involved in producing an artefact [@W3C2013PROV]. In this setting, the record includes the query that found a candidate, how it was found, any exact anchor or structural relationship, and the decision that retains, defers, or rejects it. Recording this history does not guarantee a correct result, but it makes it possible to inspect how a result was constructed and where relevant material disappeared.

## Controlled and Agentic Repository Exploration

Initial retrieval rarely provides every snippet needed to explain a behaviour. The retrieved source can reveal additional code that participates in the same flow or expose a missing link between already observed snippets. A system can therefore extend the initial evidence iteratively: a discovered call may motivate inspection of its target, an unresolved responsibility may motivate another query, and an incomplete owner may motivate a more focused source request. The central design question is who controls these decisions.

In agentic exploration, a language model observes the current context and chooses actions such as searching, opening a file, navigating to a symbol, running a tool, or stopping. ReAct demonstrates the broader pattern of interleaving model-generated reasoning with actions that obtain new information [@Yao2023ReAct]. Repository agents apply related interaction patterns to file navigation, code inspection, editing, and execution; SWE-agent, for example, shows that the design of the available commands and feedback influences how an agent operates over a repository [@Yang2024SWEAgent]. This allocation provides flexibility because the model can adapt its path to newly discovered information.

Controlled exploration keeps more responsibility in application logic. The application can construct typed actions, validate their targets, enforce per-action and global budgets, suppress repeated effects, and apply explicit stopping conditions. A model may still perform bounded semantic tasks, such as judging relevance or describing an unresolved relationship, without owning the complete retrieval state or execution policy. This makes resource use and state transitions easier to inspect, but it restricts the model's ability to improvise outside the encoded action space.

The two designs form a continuum rather than a binary distinction. An agent can operate through validated tools and fixed budgets, while a controlled pipeline can depend on model judgements at several stages. Their practical difference lies in decision ownership: which component proposes the next operation, which component determines whether it is executable, and which component decides that exploration is complete. These choices affect adaptability, auditability, failure behaviour, and cost. They do not by themselves establish which design retrieves better evidence; that requires an empirical comparison under declared conditions.

## Evidence-Grounded Learning Support

Repository evidence can support more than answer generation. When an explanation identifies the relevant source and relationships, an interaction can ask the learner to reconstruct part of that reasoning rather than only read its conclusion. Self-explanation prompts can encourage learners to connect new information with prior knowledge, identify gaps, and infer relationships; a meta-analysis reports an overall positive but heterogeneous effect across learning settings [@Bisra2018SelfExplanation]. Research on source-code comprehension likewise examines free self-explanation and Socratic prompting as ways of eliciting reasoning about code [@Tamang2021Socratic].

Evidence grounding constrains such interaction to the repository material available to the system. A `why` or `how` question can target a relationship supported by selected source, while a hint can disclose part of that relationship without inventing a missing mechanism. The same boundary requires uncertainty when the evidence is incomplete: a system should not convert a plausible retrieval result into a confident causal lesson.

This thesis treats learning-oriented interaction as the downstream motivation for the complete artifact, not as an evaluated learning intervention. The implementation can generate evidence-linked explanations and understanding checks, but the empirical study evaluates repository retrieval rather than user learning. Claims about educational benefit therefore remain grounded in prior research and require a separate user study to validate for this system.
