\section{Overall System Architecture}\label{sec:overall-system-architecture}

Guided Intelligence is organised as a policy-controlled pipeline that transforms a repository question into grounded evidence, an intent-specific response, and a guided follow-up interaction. The architecture separates six responsibilities: request and conversation-state representation, intent classification, teaching-policy control, repository retrieval, response generation, and follow-up guidance. An orchestration layer determines which stages run and passes structured outputs from one stage to the next. LLMs perform bounded tasks within particular stages, such as classifying intent, qualifying evidence, or generating a response, but they do not determine the overall execution sequence.

A run begins when the interface submits a user prompt and the permitted source selection to the local retrieval service. The service assigns a run identifier, creates a persistent run directory, checks whether the repository indexes are synchronized, and constructs a \texttt{ConversationState}. This state carries the current input together with any available conversation history, previously selected evidence, and later the classified intent context. The intent stage classifies the requested outcome, resolves the target where possible, and converts the result into a minimal retrieval-facing context. The deterministic policy stage separately decides whether the request is allowed, whether retrieval is required, which source categories may be used, and which top-level turn type should follow. A disallowed policy result terminates at a boundary response instead of entering retrieval.

Allowed requests that require repository context enter one of the configured retrieval implementations. The Workspace retrieval process is divided into three phases: initial evidence construction, bounded adaptive completion, and final evidence consolidation. Initial evidence construction converts the intent-derived evidence obligations into lexical and semantic repository searches, grounds retrieved ranges through available structural operations, and semantically qualifies the resulting source. Bounded adaptive completion then uses unresolved evidence needs and grounded leads to request additional source or relationships. Final evidence consolidation assembles and selects the evidence made available by the preceding phases. Each phase receives a bounded input and returns structured evidence or observations to the next phase; removed capabilities in the evaluated ablations change only the corresponding boundaries. Codex retrieval provides an alternative implementation of the retrieval contract and returns evidence to the same downstream orchestration interface.

The retrieval service returns a \texttt{RetrievalResult} containing ranked evidence items, a coverage status, a sufficiency judgement, and structured retrieval metadata. The control layer can then organise the evidence into a post-retrieval evidence graph before constructing a \texttt{ResponsePlan}. For an allowed request, the response plan requires an evidence-grounded response and at least one understanding check. Intent contracts define the semantic stages that the response must cover, while an LLM may arrange those stages into a coherent story flow. Deterministic validation ensures that the generated flow does not invent, omit, or duplicate required stages. Response generation receives only the resolved flow, selected evidence, and policy boundary, and produces a \texttt{ResponsePayload} containing the rendered response, source references, and guided questions.

The server also exposes a separate path that evaluates answers to generated understanding checks and returns a guided follow-up.

Logging and persistence cross all of these boundaries. The orchestration layer records intent decisions, policy outcomes, retrieval plans, evidence selection, model requests, response plans, generated payloads, violations, and completion status as structured events. The retrieval pipeline maintains its own stage and tool trace, while the server stores run metadata, evidence items, the complete orchestration result, answer evaluations, and comprehension follow-ups in the run directory. These artifacts support progress reporting in the interface and later inspection of how a response was constructed. They also preserve the distinction between deterministic control decisions, LLM decisions, and retrieved source evidence, making failures and state transitions explicit rather than embedding them only in generated prose.

\section{Intent Classification, Retrieval Context, and Source Policy}\label{sec:intent-classification-retrieval-context-and-source-policy}

Intent classification maps each request onto one or more categories from a predefined taxonomy. These labels approximate the requested outcome and provide a consistent structure for retrieval and response generation. The taxonomy was informed by empirical work on developers' information needs \cite{Ko2007InformationNeeds} and adapted to the repository-assistance tasks supported by Guided Intelligence. A request to diagnose a failure therefore remains \texttt{debug} even when retrieval must first locate and inspect unfamiliar code. The classifier supports eight task intents, summarised below.

The distinction between \texttt{explore} and \texttt{explain} reflects the difference between locating relevant focus points and understanding the larger execution relationships connecting them, as described by Sillito et al. \cite{Sillito2008ProgrammingQuestions}. Multiple intents are retained only when a request genuinely seeks several outcomes.

Beyond assigning intent labels, classification constructs the context used to begin repository retrieval. It extracts literal paths, symbols, identifiers, error messages, and other anchors from the request, proposes related search terms, and defines evidence obligations for the required response stages. The Workspace pipeline uses the anchors for exact repository grounding, combines the search terms with the obligation descriptions to construct Qdrant queries, and tracks the obligations throughout evidence construction. Schema validation rejects unknown or duplicate intents and malformed obligations, while deterministic normalization removes any target described as explicit when its name does not occur literally in the prompt. If classification cannot produce a valid result, the run stops before repository retrieval rather than substituting a deterministic classification.

Each task intent has a fixed contract that defines its retrieval purpose, semantic response stages, stopping condition, question prerequisites, and permitted form of assistance. The complete one-to-one mappings are provided in the \textbf{Implemented Intent Contract Registry} appendix. For a single intent, its stages form the required response flow. For a multi-intent request, the stage sets are combined without assigning a primary intent. An LLM may choose their presentation order, but deterministic validation requires the result to be an exact permutation of the supplied stage identifiers. It cannot add, drop, rename, merge, or duplicate a required stage. This separates semantic decisions from structural enforcement: the model determines a coherent ordering, while code verifies that every contracted part of the requested outcome remains represented.

After intent classification defines what evidence the request requires, the source policy determines where that evidence may be obtained. Source access is configured for each run through the frontend. The selected source keys are submitted with the request, validated by the backend, and converted into an allowlist of source categories and corresponding retrieval adapters. This policy prevents unselected connected sources from being queried or admitted into the resulting evidence set.

The orchestration layer can bypass repository retrieval when the conversation state already contains evidence. This branch, represented by the \texttt{retrieval\_required} decision, was intended to support evidence reuse during later conversational turns. However, the current interface creates an independent state without retained evidence for every request. Repository retrieval is therefore invoked for every submitted run, and the evidence-reuse branch remains unexercised.

\section{Learning-Oriented Interaction}\label{sec:learning-oriented-interaction}

After retrieval and final evidence selection, response generation converts the selected evidence into an intent-specific explanation. The generator receives the user request, the validated intent flow, at most sixteen selected evidence items, supported connections between those items, and the retrieval coverage and sufficiency results. The stage sequence described above serves as both the answer flow, which records the required content, and the story flow, which determines its presentation order. Generated repository claims must cite supplied evidence, whereas uncited connective sentences may only organise the explanation or state an evidence limitation. The renderer groups consecutive stages into a small number of reader-facing sections and can place supported procedures, examples, or comparisons into lists, code blocks, or tables when those forms are clearer than prose.

Understanding checks are generated in the same response-generation call so that they can target relationships actually established by the explanation. Each response contains between one and three checks, with one as the default. Additional checks are permitted only when they address a distinct and independently important reasoning transition. Each check identifies its intent, one or two target stages, the reasoning relationship being assessed, its expected answer points, and the evidence supporting that relationship. Its question form must belong to the question contract of a selected intent; for example, an \texttt{explain} check may ask how or why a supported transition occurs, whereas a \texttt{verify} check may ask what evidence establishes a claim. The complete intent-specific question mappings are recorded in the \textbf{Implemented Intent Contract Registry} appendix.

The decision to generate focused questions rather than append a generic recall prompt was informed by G-Asks, which used specific trigger questions to support learning through writing \cite{Liu2012GAsks}. Guided Intelligence does not reproduce the G-Asks question taxonomy. Instead, it separates the requested task, the reasoning transition being assessed, and the permitted question form. This separation is also consistent with the multidimensional treatment of communicative functions in ISO 24617-2, although the system does not implement the standard's dialogue-act annotation language \cite{ISO24617_2_2020}.

Every understanding check includes a three-step hint ladder. The \texttt{direction} hint identifies the next reasoning operation without supplying the answer; \texttt{focus} points to the relevant component, stage, or evidence relationship; and \texttt{scaffold} reveals the beginning of the connection while leaving at least one expected answer point unresolved. Generated questions and hint ladders are deterministically validated against the selected intent contracts and supporting evidence. Invalid output receives one isolated LLM repair attempt. If the repaired output remains invalid, response generation fails explicitly rather than silently removing the checks or substituting deterministic questions.

The intent contracts also provide an assistance boundary to the response generator. These boundaries distinguish, for example, explaining an implementation from completing a requested change, or identifying review findings from automatically rewriting the reviewed artifact. They constrain the generation prompt but are not a separate deterministic enforcement mechanism. Structural validation can establish that all contracted stages and evidence references are present; it cannot by itself prove that the generated prose has respected a semantic assistance boundary.

After reading the initial response, the user can submit answers to its understanding checks through the frontend. This starts a separate answer-feedback path tied to the original run; it is not treated as an arbitrary new message in a continuing conversation. An answer-evaluation LLM compares each submission with the expected answer points and classifies it as correct, partial, incorrect, or unanswered. The evaluation records what the answer covered, what it missed, and which reasoning requires attention. The system combines these results with the original response flow and checks to create a structured follow-up context. A partial or incorrect answer directs the resulting feedback towards repairing the missing reasoning, while a correct answer can lead to a deeper check. If neither repair nor further deepening is selected, the guided interaction is completed. The answer-feedback generator may also return a revised check, which must satisfy the same intent-specific question and hint contract as the original.

The final retrieval campaign disabled response generation and therefore did not evaluate the explanation, question, or follow-up stages. Initial explanation and question generation were exercised during development. Isolated tests covered answer evaluation and teaching-state construction, while the server persistence test used a mocked follow-up generator. No retained run contains a complete generated follow-up artifact. These components are consequently described as implemented interaction support rather than empirically validated learning behaviour, and the study makes no claim that they improved user comprehension.

\section{Repository Retrieval Capabilities}\label{sec:repository-retrieval-capabilities}

The Workspace pipeline uses four kinds of repository operation: hybrid search over indexed source ranges, inspection of source at known locations, CodeGraph structural queries, and language-specific source analysis. Their results are treated as candidates rather than automatically accepted as evidence. Later stages compare the retrieved source with the evidence obligations derived from the request and determine which ranges provide relevant support.

Qdrant is the active backend for both lexical and semantic retrieval. Repository chunks are indexed with a dense embedding and a stored sparse vector. At query time, the semantic query is embedded, the lexical query is converted into a sparse vector, and Qdrant combines the two ranked result sets using reciprocal-rank fusion. The two query texts may differ: obligation descriptions provide the semantic formulation, while identifiers and other literal terms can be preserved in the lexical formulation. Searches can also be restricted to particular paths or source categories. The returned items remain source ranges with path, line, text, score, and retrieval-channel information; hybrid rank is treated as a discovery signal rather than evidence of semantic relevance.

Exact inspection is used once retrieval or structural analysis has identified a concrete file and approximate location. The \texttt{open\_file} operation accepts a repository-relative path and a bounded line window and returns overlapping indexed source snippets. It therefore allows the pipeline to inspect source surrounding a known lead without broadening the search through another semantic query. Exact-symbol lookup is provided separately by CodeGraph and can identify structural nodes matching an identifier. These operations serve different purposes: opening a file exposes the requested source range, whereas exact-symbol lookup attempts to attach a repository identifier to a structural entity.

CodeGraph supplies the structural layer. It resolves retrieved ranges to enclosing owners, exposes file outlines, and represents relationships such as calls, references, dependencies, and file-level neighbourhoods. The pipeline can inspect callers and callees, expand selected relationship types, test whether two files have a recorded relationship, and search for qualified references. This layer is intended to convert isolated textual matches into named implementation responsibilities and to expose cross-file transitions that lexical or semantic similarity alone may not reveal. CodeGraph is therefore used to identify and verify possible connections, not as standalone evidence; any relationship retained by the pipeline must be grounded in inspectable source.

Language-aware source analysis supplements this graph representation. A single router dispatches TypeScript, JavaScript, and their related extensions to an adapter based on the TypeScript compiler API, while Python and Python stub files use the standard-library AST. The adapters identify owner boundaries and calls within an owner directly from source. They also recover assignment-defined functions that may lack a suitable CodeGraph owner, including top-level JavaScript or TypeScript function assignments and Python lambda assignments. These recovered owners remain source-derived records rather than additions to the CodeGraph index. The router provides a common contract for these operations, allowing another language-specific adapter to be added without changing the pipeline stages that consume its results. The implemented adapters were limited to the Python and TypeScript language families represented in the evaluation repositories; support for additional languages was therefore left unimplemented and untested.

\section{Initial Evidence Construction}\label{sec:initial-evidence-construction}

Initial evidence construction converts the request's repository obligations into the source observations available at round zero. Before broad retrieval, literal paths and symbols extracted during intent classification are checked against the repository. Confirmed anchors can supply exact source leads and constrain the searches associated with an obligation; unresolved or ambiguous symbols instead become additional query terms. Each repository obligation then produces one Qdrant request with a semantic formulation and a lexical formulation that preserves applicable identifiers. Dense, sparse, and fused results are retained separately in the trace even though the fused ranking is the primary returned result.

The initial search does not immediately discard all but one range from each file. For every obligation, the pipeline forms file groups from the dense and sparse result channels, records a representative range for each file, and retains other returned ranges as alternatives. These ranges are combined with exact-anchor leads from the request. Identical path and line-range occurrences are then deduplicated globally before structural resolution, so a range retrieved through several obligations or channels is submitted to CodeGraph only once.

CodeGraph maps each unique range to the narrowest applicable structural owners. A retrieved range can produce no owner, one owner, or several plausible owners, and every applicable range-owner pairing remains available at this boundary. The pipeline converts these results into a canonical snippet pool. Observations referring to the same structural node are merged, while unresolved observations use their exact source range as identity. The merged record retains the obligations, queries, channels, ranks, scores, and exact anchors through which the source was found. Nested owners covering the same retrieved material are represented by the narrower owner while retaining the enclosing owner as context.

The canonical snippets are ranked for admission to the initial owner-comparison request. The ordering gives priority to obligation coverage, exact anchors, recurrence across distinct queries, retrieval rank, and score. Admission is measured against the serialized request size rather than a fixed number of files or candidates: snippets are appended individually until the preferred input threshold is crossed, with the crossing snippet retained. File grouping is used to present competing owners coherently to the model, but it does not constitute a separate per-file ranking rule. Snippets outside the admitted request remain recorded as deferred observations.

The owner-comparison LLM selects a primary owner and, where justified, semantically distinct additional owners from the admitted groups, subject to the global round-zero limit. This decision resolves competition among retrieved owners but does not yet classify any selected source as evidence. Owners not selected at this stage are recorded as dormant rather than silently removed. The selected owners are then disclosed with source aligned to their structural boundaries and fitted to the qualification input budget. A separate qualification LLM classifies each disclosed observation as a retained direct fact, a retained or deferred navigation lead, or insufficient material. It also records which obligations the visible source contributes to and which, if any, it establishes by itself. Retained observations form the grounded round-zero candidate set; deferred and dormant observations remain available to the later controller under their respective recovery rules.
